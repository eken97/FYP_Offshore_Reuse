# Pipeline

What runs, in what order, reading and writing what. This is the map; the
reasoning behind the choices is in [decisions.md](decisions.md), and the
things that will bite you are in [traps.md](traps.md).

---

## Shape of the thing

```
  OpenFAST campaign                     post-processing
  ─────────────────                     ───────────────
  69 metocean bins                      Stage 0  QA sweep
    × 6 seeds                           Stage 2  stress → rainflow → histograms
    = 414 runs            ──.outb──▶    Stage 3  Miner → damage → life
                                        Stage 4  L0–L4 reuse classification
                                                 ↓
                                        results/ + figures/
```

Two parallel tracks share that skeleton:

- **Member track** — 112 members, damage at each end, 16 circumferential
  points per end. Quantitative.
- **Joint track** — 120 brace-to-chord connections, hot-spot stress via
  parametric SCFs. Indicative, first-order. The distinction matters; see
  [limitations.md](limitations.md).

## Stage by stage

### Stage 0 — QA (`stage0_qa.py`)

Walks the run folders and checks each one before anything trusts it:
simulation reached its intended duration, terminated normally, the geometry
matches, environmental channels are sane. Writes `stage0_qa.csv`. Read-only,
so it is safe to run while a campaign is still executing.

### Geometry (`sd_geometry.py`, `joint_geometry.py`)

`sd_geometry.py` parses the SubDyn input deck into member/joint topology plus
section properties (area, second moment, section modulus), and classifies
members by zone (atmospheric / splash / submerged / buried). It also provides
the corroded-section helper used by the corrosion tracks.

`joint_geometry.py` is the joint-track equivalent and considerably larger: it
resolves connectivity, classifies each joint into the K / X / Y families,
computes the DNV Appendix B non-dimensional parameters (β, γ, τ, θ, ζ, α) per
connection, and establishes the in-plane / out-of-plane bending reference
frame.

### Stress recovery (`stress.py`)

For the member track, at each of 16 circumferential angles θ:

```
σ(θ,t) = N/A + Mkx·cos θ / W − Mky·sin θ / W
```

Never written to disk — it exists only inside a Stage-2 worker. For the joint
track, `hotspot_joint()` superposes axial, in-plane-bending and
out-of-plane-bending components with their respective SCFs following
DNV-RP-C203 §3.3.1.

### Rainflow (`rainflow_hist.py`)

Cycle counting (ASTM E1049, via the `rainflow` package), binned into 256
log-spaced bins from 0.01 to 1000 MPa. Each bin stores both the cycle **count**
and the exact power sums Σ(range^m) for every Wöhler exponent in use.

Storing the power sums, not just counts, is what makes the cache reusable: a
later change to an S-N curve constant needs only Stage 3 to re-run. See
[decisions.md](decisions.md#the-stage-2-cache-stores-power-sums-not-just-counts).

### Stage 2 — per-run histograms (`stage2_*.py`)

One `.npz` plus a JSON provenance sidecar per run/seed, roughly 9 MB each,
3.6 GB for the full campaign. Six variants exist: member and joint tracks,
each optionally with corrosion and/or the can-thickness retrofit composed on
top.

**This is the only durable intermediate.** Everything upstream is recomputed
from `.outb`; everything downstream is recomputed from these.

### Stage 3 — damage and life (`stage3_*.py`)

Miner summation per bin, averaged across the 6 seeds, weighted by each bin's
occurrence probability from `data/oc4_k13_bins.csv`, scaled to a 25-year
design life. Writes the damage tables in `results/`.

### Stage 4 — reuse classification (`stage4_reuse_classification.py`)

Applies the L0–L4 acceptance ladder to each member and bay. See
[reuse-criteria.md](reuse-criteria.md).

### Static / ULS side-branch

A separate, shorter chain that turned out to matter more than expected:

```
member_force_extremes.py  → max tension/compression across all 414 runs
member_static_life_check.py → EN 1993-1-1 + DNV-ST-0126 buckling check
member_power_law_fit.py   → fits D(T) = A·T^p per member
member_remaining_life.py  → min(fatigue life, static life) = governing life
```

The finding that the static check, not fatigue, governs for much of the
structure came out of this branch.

## File formats

| Format | Where |
|---|---|
| `.outb` | OpenFAST binary output. Read by `outb_reader.py`, which pulls only the ~672 force/moment channels needed rather than all ~2767. Never deleted, never committed. |
| `.dat` | SubDyn input deck (geometry, section properties) |
| `.sum.yaml` | SubDyn summary output — direction cosine matrices for the joint track. Generated by a run; can be very large (one was 112 MB). |
| `.npz` + `.json` | the Stage-2 histogram cache and its provenance sidecar |
| `.csv` | every Stage 3 / Stage 4 / final table, in `results/` |
| `.png` + `.svg` | every figure, written as a matched pair by `fatigue_style.py` |

### Regenerating figures always shows a dirty tree

Re-running a figure builder produces PNG and SVG files that are **visually
identical but not byte-identical** to the committed ones. Matplotlib embeds a
generation timestamp and assigns element IDs that vary between runs, so
`git status` will report every regenerated figure as modified.

That is expected and is not evidence that anything changed. If you want to
confirm a code change did not alter a figure, compare the underlying numbers
in `results/` rather than the image bytes — or run
`python scripts/run_example.py`, which compares numbers and not pixels.

## The worked example

`data/example/` holds one Stage-2 member-track cache: condition
`LC_V20_H3p5_T8` (V = 20 m/s, Hs = 3.5 m, Tp = 8 s), seed `S100001`.

```bash
python scripts/run_example.py
```

runs Stage 3 over it and compares against `expected_stage3_member.csv`.

**Read this part.** The example holds **1 of the campaign's 69 bins**, at
**1 of its 6 seeds**. The damage numbers it produces are the arithmetic of a
single condition carried through the real code path. They are *not* the
thesis results and they are not comparable to anything in `results/`. Treat
the example as proof that the pipeline runs and stays numerically stable —
a regression test — and nothing more.

Why not ship more? The full Stage-2 cache is 3.6 GB and the raw output it
derives from is 119 GB. Neither belongs in a git repository.

**The joint track has no worked example.** It needs a SubDyn `.sum.yaml`,
which only exists as the output of an actual OpenFAST run and can run to
hundreds of megabytes. Shipping joint-track input data that cannot be used
would be worse than shipping none, so the joint-track *results* are in
`results/` and the joint-track *inputs* are not.

## Running order for a full rebuild

```
scripts/fetch_openfast_inputs.py     stage the NREL decks
simulation/plan_assignment.py        divide the work
simulation/campaign.py               build + run 414 cases   (~weeks)
postprocessing/run_pipeline.py       Stage 0 / 2 / 3, all tracks   (~hours)
postprocessing/stage4_reuse_classification.py
postprocessing/final_results_member.py
postprocessing/final_results_joint.py
postprocessing/report_figures_*.py   figures
```

`run_pipeline.py`'s `SELECT` dict controls which stages and tracks execute.
Stages are individually skippable, which matters when a single track takes
four to ten hours and you do not want to redo the ones that already
completed.
